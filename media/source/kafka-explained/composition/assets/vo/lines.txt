This is a short explainer on Kafka, and how Tallyproof uses it.
Kafka is a distributed log. Producers append messages to a topic. Consumers read them in order, at their own pace, and remember how far they got. Messages are kept, not deleted on read, so a stream can be replayed. Tallyproof runs Redpanda, a Kafka-compatible broker in a single binary, so the whole stack starts on a laptop with one command.
The main topic is fin dot events dot raw, with six partitions. Events are keyed by award, so everything about one award lands on the same partition, in order. The replay producer publishes the gold events, and a live connector adds the Treasury's daily cash statement.
The ingestion consumer validates every message against a JSON schema from the registry, predicts duplicates with a per-partition Bloom filter, and lets the database decide: a unique key on the ledger refuses any repeat. Malformed records go to a dead-letter topic instead of being dropped. The consumer stores its offset in the same transaction as the append, so a crash can never double count or skip.
Measured on the laptop: twenty thousand events published in four seconds using seventy-two megabytes, all landing with gap-free leaf indexes. About three thousand events a second into the ledger. Replaying the same stream again appends nothing.
Why Kafka at all? It decouples the producers from the single-writer ledger, buffers bursts, and makes every run replayable. One lesson from building it: derived views used to consume from Kafka too. They now read the ledger directly, in leaf order, because that is the signed source of truth, and it gives exactly-once output for free. Kafka carries what leaves the database: appended events, breaks, and checkpoints, for the live stream and outside consumers.
In the repository, look at the ingestion app for the consumer, deduplication, offsets and dead letters; the replay module for the producer; and the compose file for the broker and its topics.
