# Evaluation

This document explains how Tallyproof measures the quality of its answers, and how CI stops a change from making them worse.

## Principles

**Expected answers are exact.** They're computed from the data and the anomaly labels, never produced by an LLM.

**The oracle is independent.** Expected values come from `backend/evals/oracle.py`, a plain Python implementation that works directly on the cleaned data and the label manifest. It shares no code with the analyst: not its query compiler, not its views, not its reconciliation rules. If the two shared a bug, a wrong answer could pass. Keeping them apart prevents that, and a test fails if importing the oracle pulls in any analyst, Django, or reconciliation module. It also has to agree with every hand-checked held-out answer.

Each expected answer lists the events a complete answer must cite and the events it may cite without being wrong (for an anomalous outlay, the award behind it), so citation recall and precision are both well defined.

**Deterministic checks come first.** Anything that can be scored exactly is. An LLM judge is planned for one thing only, whether the prose connecting claims is supported, with its prompt and model versioned. Until it exists, narrative faithfulness isn't reported, and the verifier's structural rules (no free numbers, every sentence bound to a value or a citation) are the only checks on the prose.

**Thresholds only go up.** They live in `backend/evals/thresholds.toml`. Today they hold the planned first-milestone values, which the latest smoke run passes. Once the full run sets them from its baseline, lowering one needs a written decision record.

**Results are labeled honestly.** Runs that use the fake LLM client test the evaluation harness, not answer quality. They're labeled as harness checks and never published as quality results.

## Dataset

Questions are asked about a small committed dataset in `testdata/eval/`, so every run, local or CI, sees the same data. It holds whole real awards from the USAspending gold build, every obligation, modification, and outlay for each, picked by a hash of the award key and spread across the twelve agencies with the most paid awards. Labeled anomalies are then mixed in with a fixed seed, three of each type. `manifest.json` records the counts, and `make eval-dataset` rebuilds it from a local gold build.

## Question sets

Each question has a stable ID, the question text, a category, the expected answer (a decimal amount, a set of event IDs, a yes or no, an exact policy quote, or a refusal), the events a correct answer must cite, and whether it should be refused.

| Category | Example | Expected |
|---|---|---|
| Numeric aggregate | "How much did the Department of Energy obligate to recipient X in FY2025?" | An exact amount, citing the contributing obligations |
| Record lookup | "When was award Y last modified, and by how much?" | A date and an amount, citing the modification |
| Anomaly list | "Which awards had outlays exceeding their obligations last quarter?" | A set of awards, citing the events involved |
| Policy | "What does the FAR say about modifying a fixed-price contract?" | An exact quote from the cited regulation text |
| Refusal | "How much will this agency spend next year?" or "What is this executive's salary?" | A refusal with a reason |
| Injection | A question about an award whose description contains planted instructions | The correct answer, unaffected by the planted text |

The smoke set has 20 fixed questions that cover every category (`backend/evals/questions/smoke.toml`). The full set has 178 (`full.toml`): every non-lookup template filled with real agencies, periods, and FAR sections, plus 80 lookups. Both are generated by `python -m evals.golden` from the committed dataset, and a test fails if the files drift from a rebuild. Questions come from templates with paraphrased variants, which helps against prompts tuned to one wording, but paraphrases of a template aren't truly new questions.

### Held-out questions

A frozen set of 40 free-form questions (`backend/evals/questions/held_out.toml`) was written before any prompt or router tuning, and it's never used for tuning. A test pins the file's hash, so changing a question has to be deliberate. So far all 40 were written by the author; questions from someone else are planned for the final phase, added word for word. Expected answers come from the oracle, and ten of them are also checked by hand. Every report shows the gap between template and held-out scores. A large gap means the system is overfit to its templates, and that gets reported, not hidden.

## Metrics

| Metric | How it's computed |
|---|---|
| Citation precision | Cited events that should have been cited, divided by all cited events. For policy questions the unit is the FAR section, and sections in the expected section's subpart count as correct. Anomaly lists are left out: the real data holds anomalies nobody planted, which reconciliation rightly finds but the labels can't know about. Those extra findings are counted separately |
| Citation recall | Events that should have been cited and were, divided by all events that should have been cited |
| Numeric exactness | Answers whose bound value matches the expected amount to the cent |
| Reconciliation recall | Labeled anomalies caught by the reconciliation rule of the right type. Precision isn't computed: the real data holds anomalies nobody planted, which the rules rightly find but the labels can't know about, so findings beyond the labels are counted instead |
| Analyst anomaly recall | Expected anomalies the analyst listed, divided by all expected anomalies |
| Answer coverage | Answerable questions that got an answer |
| Refusal correctness | Precision, recall, and F1 of refusals |
| Free-number and repair rates | How often the model typed a number before the verifier stopped it, and how often a retry fixed it |
| Quote faithfulness | Policy quotes that appear exactly in the cited document |
| Narrative faithfulness | Planned: an LLM judge's score for whether the prose is supported by the cited evidence. Not reported yet |
| Injection resistance | Injection questions answered correctly without following the planted instructions |
| Fallback rate | Numeric questions that needed the lower-assurance SQL fallback instead of the query spec |
| Sampled and too-broad rates | Answers whose citation listed only some of the records behind a total, and answerable questions refused because their records passed the citation cap |
| Cost and latency | Tokens, and p50 and p95 latency per question. Cost isn't estimated, since the live provider is a free tier |

Two scoring rules keep the numbers honest. Every quality metric counts all answerable questions, so a refusal on an answerable question is a miss, and refusing whenever in doubt can't inflate precision. And integrity checks are reported separately from quality: proof verification, numbers left after the verifier, and tamper detection are guaranteed by how the system is built. They show the wiring works. They say nothing about whether answers are good, and they're never presented as if they did.

## Running evaluations

```bash
make eval SET=smoke MODE=cached
```

`SET` is `smoke`, `full`, `held_out`, or `all` (full plus held-out). `MODE` is `fake` (scripted responses), `cached` (recorded responses), or `live` (real model calls).

`SCALE=demo` runs the same pipeline on the first 20,000 gold events, the slice the local demo streams, instead of the committed dataset. That's where totals pass the 1,000-record citation cap, so it measures the sampled and too-broad rates at the size people actually see. Its questions are generated from the slice by the same template builder, plus a total and a count for the two largest agencies and a ranking of every agency; the oracle computes every expected answer. The slice is built locally from a gold build with `make eval-dataset SCALE=demo` and isn't committed.

Each run builds its own ledger in a throwaway Postgres container, with the same image, roles, and migrations as production. It loads the evaluation dataset and the FAR leaves, runs the journal and reconciliation projections, and signs one checkpoint with a key used only for evaluations. Every question then goes through the real pipeline as the read-only analyst role, and every cited event is checked the way a browser would: its bytes hash to its leaf and its inclusion proof verifies against the signed root. The runner lives in `backend/evals/runner.py` and needs Docker (Colima locally).

The LLM client sits behind an interface with three implementations: a scripted fake, the real client, and a caching wrapper. The cache key is a hash of the model ID, prompt version, prompt bytes, and parameters, so changing a prompt invalidates exactly the entries it affects. Token and cost budgets per run stop the runner with a clear error before it overspends.

Each run writes a machine-readable JSON report and a readable Markdown report to `var/eval/<timestamp>/`, and CI keeps both as artifacts. The reports, not database rows, are the record of a run, since each run's database is thrown away; the dashboard reads them. Publishing a run to the dashboard is a deliberate step: `make eval-export REPORTS=var/eval/<timestamp>/report.json` copies the report to `frontend/public/replay/evals/` and rebuilds the index there, and the copy is committed through a normal pull request. The export refuses harness checks and any report carrying contact details. The site's evaluation page reads those reports: every run across every quality metric as parallel coordinates you can filter by dragging an axis, each metric over runs as a horizon chart around its gate, a slope chart of per-category results between any two runs, and a matrix of every question in every run, with integrity shown apart from quality. Thresholds live in `backend/evals/thresholds.toml`, and the process exits non-zero when a gated metric falls below its threshold.

## In CI

| When | Questions | Mode | Gate |
|---|---|---|---|
| Every pull request (`eval-smoke`, part of `ci-gate`) | Smoke set | Cached. Uncached items fall back to the fake client and the run is labeled a harness check | Integrity always; every quality threshold when every response is recorded. A harness check fails the pull request if it touches the analyst, the question sets, the policy corpus, or the evaluation dataset (`scripts/ci/check_eval_recordings.py`); record fresh responses with `make eval-record` |
| Weekly (scheduled trigger, Sundays 03:00 UTC) | Full and held-out sets | Live, with the key from the `llm-eval` context | Fails on regression; reports kept as artifacts |
| Release tag | Full set | Live | Planned with the first release |

Pull request pipelines never receive the model key: the `llm-eval` context is restricted to the `main` branch and the scheduled job, so a pull request, forked or not, can only replay recordings.

## Starting thresholds

| Metric | First milestone | 1.0 release | Gated today |
|---|---|---|---|
| Citation precision | 0.90 | 0.95 | Yes |
| Citation recall | 0.80 | 0.90 | Yes |
| Numeric exactness | 0.95 | 0.98 | Yes |
| Refusal F1 | 0.85 | 0.90 | Yes |
| Analyst anomaly recall | 0.85 | 0.90 | Yes |
| Answer coverage | 0.80 | 0.90 | Yes |
| Quote faithfulness | 1.00 | 1.00 | Yes |
| Injection resistance | 0.90 | 0.95 | Yes |
| Reconciliation recall | 1.00 | 1.00 | Reported |
| Held-out numeric exactness | reported only | 0.90 | Reported |

Integrity checks must always pass completely, and any failure blocks a merge.

These were educated guesses before any live run, and the smoke run passes all of them. The full run of every question sets each threshold to its measured baseline minus a small margin; after that they only go up.

## Comparing against a naive baseline

Planned: the same questions run through a naive RAG setup, retrieving the top rows and documents and letting the model answer and cite freely, with no slots and no verifier, scored by the same oracle. Shown beside the real results, it would make plain what the query spec, the bound values, and the verifier contribute. It isn't built yet, so no comparison is claimed.

## The README results table

`python -m evals.readme_table <report.json> <commit>` regenerates the table between `<!-- eval-table:start -->` and `<!-- eval-table:end -->` from a quality run, and refuses a harness check, so a placeholder can never be published as a result. The table lists the model IDs, date, number of questions, git commit, and template and held-out scores side by side. The weekly job keeps each report as a CI artifact; the table is updated through a normal pull request, never by pushing to `main`.
