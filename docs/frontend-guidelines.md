# Frontend guidelines

## Design direction

The interface should feel like an instrument panel for an auditor: calm, precise, and easy to scan, with strong contrast for data. Motion appears only where it explains cause and effect, like a record turning into a leaf, a hash climbing to the root, or a check failing. No gradient-heavy startup styling and no glass effects.

Verification state is the core visual language. Verified is green, failed is red, pending or unverified is neutral, and refused is amber. Each state always pairs color with an icon and a word, so nothing depends on color alone.

Hashes appear in a monospace font, shortened in the middle (`3f9a…c21e`), with the full value on hover or focus and a copy button.

## Design tokens

Every color, shadow, radius, and duration is a CSS custom property in `frontend/src/styles/tokens.css`, and both themes are defined there together. The light palette is the default on reading pages; the landing story opens dark. A chart set of six colours, distinguishable under the common forms of colour-blindness and re-tuned for each background, sits beside the interface colours, and verification state in a chart always uses the state colours, never a series colour. The shape of the file:

```css
:root {
  --bg: ...; --bg-elevated: ...; --fg: ...; --fg-muted: ...;
  --border: ...; --accent: ...;
  --ok: ...; --fail: ...; --warn: ...; --info: ...;
  --font-sans: ...; --font-mono: ...;
  --radius-sm: 4px; --radius-md: 8px;
  --shadow-1: ...;
  --dur-fast: 120ms; --dur-base: 240ms; --dur-story: 900ms;
  --ease-standard: cubic-bezier(.2, 0, 0, 1);
}
[data-theme="dark"] { /* every token redefined */ }
@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { /* the same */ } }
```

Tailwind reads these through `@theme` in `globals.css`. Components never use raw color values. Components are built the way shadcn/ui builds them (variants through `class-variance-authority`, classes merged with `cn`), copied in by hand under `components/ui/` rather than generated by the shadcn command.

The theme switch cycles system, light, and dark, stores the choice in the browser, and an inline script in the root layout applies a stored choice before the first paint so nothing flashes.

## Typography

Inter for the interface and JetBrains Mono for hashes, amounts, and IDs, both self-hosted at build time through `next/font`. Sizes come from a fluid scale (`--text-xs` to `--text-hero`) that grows with the viewport between a floor and a ceiling. Money always uses tabular numerals, sits right-aligned in tables, and shows its currency.

## Layout

Layouts are built mobile first. The breakpoints 375, 768, and 1280 pixels are where a layout changes shape; between them everything is fluid: percentages, `clamp()`, `minmax()`, and grids that fit as many columns as the width allows. The rules every component follows:

- Width is the only axis that changes layout. No fixed pixel widths on containers, cards, or images.
- Full-height sections use `100dvh`, never `100vh`, so a phone's browser bar can't push content off screen.
- The page never scrolls sideways. Long identifiers wrap or truncate in the middle; wide tables and the proof tree scroll inside their own container; images never exceed their box.
- A component that changes shape at a breakpoint (the navigation folds into a menu below 768, the proof tree becomes a vertical list of hops on phones, a table becomes cards) is designed and approved in every form. Otherwise it is the same component at every width.
- Behaviour follows capabilities, not device names: hover effects only under `(hover: hover)`, touch targets of at least 44 pixels under `(pointer: coarse)`, motion follows `prefers-reduced-motion`.

A browser test enforces the first three rules: every page is opened at six viewports (a tall phone, a short phone, a phone on its side, a tablet, a laptop, a desktop) in both themes, plus a laptop at 200 percent zoom, and the build fails if any page can scroll sideways.

## Motion

- Motion (the library) handles component state changes. GSAP with ScrollTrigger and Lenis drive the landing page story only, and both load lazily on that route (`lib/motion`).
- Every animation shows what caused what. Nothing loops for decoration.
- With reduced motion enabled, movement becomes a fade or an instant change.
- The landing story never blocks interaction, runs under six seconds, and can be skipped.

## Accessibility

- Every interactive element can be reached by keyboard and shows a visible focus ring.
- Text meets WCAG AA contrast in both themes, checked automatically on every page in the browser tests with axe.
- Verification results are announced through a live region.

## Code structure

```
frontend/src/
  app/                 routes (App Router)
  components/          site chrome (navigation, theme switch, footer) and ui/ primitives
  features/<feature>/  components, hooks, and a README per feature
  lib/verify/          canonical JSON, hashing, Merkle verification, Ed25519
  lib/api/             typed client generated from the OpenAPI schema
  lib/replay/          loader for the public demo bundle
  styles/tokens.css
frontend/e2e/           browser tests (Playwright, axe)
```

The API URL, WebSocket URL, and mode (`live` or `replay`) come from environment variables. No hostnames are hardcoded.

## Rendering answers safely

Model output is never rendered as HTML or Markdown. An answer arrives as plain text segments plus typed claim components, which closes off links and images as a way to leak data ([threat-model.md](threat-model.md)).
